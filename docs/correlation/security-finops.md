# CloudPulse Specification — Security ↔ FinOps Correlation Contract

## 1. Document Overview & Architectural Identity

* **Document ID**: `CORRELATION_SECURITY_FINOPS_CONTRACT`
* **Target Consumer**: Siddu (Implementation Engineer) & Incident Orchestrator
* **Target Service**: `services/detection-worker`
* **Subsystem**: Security ↔ FinOps Correlation Engine (`services/correlation/` & `services/incident_orchestrator.py`)
* **Status**: Specification Only (Contract for Siddu — No Code or Schema Changes)

### Core Purpose
CloudPulse operates as an Azure-based Autonomous FinOps & Threat Surface Triage Engine. While security detectors (`RESOURCE_CREATION`, `UNEXPECTED_PUBLIC_EXPOSURE`, `SUSPICIOUS_OUTBOUND_ACTIVITY`) identify threat activity across the control and data planes, and the FinOps detector (`COST_ANOMALY`) identifies abnormal financial expenditure, the **Security ↔ FinOps Correlation Engine** bridges these two independent domains.

Its sole purpose is to deterministically determine whether independently detected **Security Findings** and **FinOps Findings** are sufficiently related in resource scope, timing, and evidence profile to be synthesized into a **Correlated Incident**.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          RESPONSIBILITY SEPARATION                          │
├──────────────────────────┬──────────────────────────────────────────────────┤
│ Detection Layer          │ Answers: "What happened?"                        │
│ (Security & FinOps)      │ Produces independent, immutable Finding records. │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ Correlation Layer        │ Answers: "Are these findings related?"           │
│ (This Specification)     │ Evaluates deterministic resource, temporal, and  │
│                          │ categorical dimensions. Updates Incident model.  │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ AI Triage Layer          │ Answers: "What does this mean & what should we   │
│ (Future Milestone)       │ do?" Synthesizes narrative and root-cause analysis│
├──────────────────────────┼──────────────────────────────────────────────────┤
│ Remediation Layer        │ Answers: "How do we stop it?"                    │
│ (Future Milestone)       │ Executes human-approved mitigation actions.      │
└──────────────────────────┴──────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **Core Design Principle: Correlation is NOT Proof of Causality.**
> CloudPulse asserts: *"These findings are strongly correlated based on resource, timing, and evidence concurrence."* It must **never** claim: *"This security event caused the cost increase."* Causality assessment, attribution, and intent belong strictly to subsequent contextual analysis and the AI triage layer.

### Required Finding Fields (Common)
Every evaluated finding must supply:
* `finding_id`: Deterministic unique identifier (`F-RC-...`, `F-UPE-...`, `F-SOA-...`, `F-COST-...`).
* `finding_type`: String detector contract identifier.
* `timestamp`: ISO-8601 UTC timestamp of detection.
* `severity`: `SeverityLevel` enum (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`).
* `confidence`: Float score between `0.0` and `1.0`.
* `resource`: `ResourceInfo` containing canonical `id`, `name`, `type`, and `resource_group`.
* `identity`: `IdentityInfo` containing `caller`, `principal_id`, and `principal_type`.
* `evidence`: `EvidenceInfo` containing subsystem evidence fields.

## 3. Correlation Dimensions

Correlation is evaluated across five distinct, deterministic dimensions. No single dimension is evaluated in isolation.

```
                               Correlation Dimensions
                                         │
        ┌───────────────────┬────────────┴───────┬───────────────────┐
        ▼                   ▼                    ▼                   ▼
  1. Exact Resource   2. Categorical       3. Temporal         4. Identity /
     Boundary            Compatibility        Alignment           Context
     (resource_id)       (cost_category       (D_eval vs          (caller UPN /
     Weight: Primary     vs anomaly_type)     T_event)            principal)
```

### A. Dimension 1: Exact Resource Correlation (Primary)
* **Condition**: `security_finding.resource.id.strip().lower() == cost_finding.resource.id.strip().lower()`
* **Weight**: **Highest**. The fundamental anchor of CloudPulse correlation is the canonical Azure Resource ID.
* **Invariant**: Workloads provisioned in cloud environments (VMs, Container Apps, Database instances) are uniquely identified by their ARM resource ID. Exact resource matching provides the necessary foundation for high-confidence correlation.

### B. Dimension 2: Resource Group Correlation (Contextual Only)
* **Condition**: `security_finding.resource.resource_group.lower() == cost_finding.resource.resource_group.lower()` where `resource.id` differs.
* **Weight**: **Supporting / Contextual Only**.
* **Constraint**: A resource group match across distinct resources (e.g. security finding on VM-A, cost surge on VM-B) **must never produce a STRONG or VERY_STRONG correlation**, and must **never** automatically escalate an incident to CRITICAL. It represents structural proximity, not direct evidence concurrence.

### C. Dimension 3: Subscription Correlation (Insignificant)
* **Condition**: Same `subscription_id`, but different resource IDs and resource groups.
* **Weight**: **Zero**.
* **Constraint**: Co-location in the same Azure subscription is statistically meaningless in multi-workload enterprises. Subscription-level co-occurrence produces `CorrelationStrength.NONE`.

### D. Dimension 4: Temporal Correlation (Latency-Aware)
* **Condition**: The security event's occurrence aligns with the billing evaluation period.
* **Latency Reality**: Azure Cost Management data is subject to an 8–24 hour processing lag. Therefore, correlation **must never compare ingestion timestamps**.
* **Window Specifications**:
  1. **`SUSPICIOUS_OUTBOUND_ACTIVITY` ↔ `COST_ANOMALY`**:
     * The security flow occurred on the same UTC calendar day as `cost_finding.evidence.evaluation_date`, OR within the 24 hours immediately preceding it:
       $$\text{Flow Date } D(T_{\text{flow}}) \in [D_{\text{eval}} - 1\text{ day},\ D_{\text{eval}}]$$
     * *Rationale*: Flow telemetry occurs in real-time on day $D$. The Azure billing engine aggregates and bills that egress on day $D$, but emits the finalized record on day $D+1$.
  2. **`RESOURCE_CREATION` ↔ `COST_ANOMALY`**:
     * The resource was created within **7 days** prior to `evaluation_date`:
       $$T_{\text{creation}} \in [D_{\text{eval}} - 7\text{ days},\ D_{\text{eval}}]$$
     * *Rationale*: Newly created resources ramp up utilization, incur recurring baseline charges, or launch initial jobs within their first week of life.
  3. **`UNEXPECTED_PUBLIC_EXPOSURE` ↔ `COST_ANOMALY`**:
     * The exposure event was detected within **7 days** prior to, or concurrent with, `evaluation_date`.

### E. Dimension 5: Identity Correlation (Supporting Context)
* **Condition**: `security_finding.identity.caller` matches an active principal associated with the resource creation or configuration change.
* **Weight**: **Supplemental**.
* **Constraint**: Cost Management findings do not carry caller identities (`caller = "azure-cost-management"`). Identity matching cannot be a hard requirement, but where a control-plane security finding shares an explicit caller, it reinforces control-plane context.

## 4. Deterministic Correlation Matrix

The engine evaluates pairs of findings against a deterministic rule matrix:

| Finding Pair | Category / Evidence Pre-requisite | Temporal Requirement | Resource Requirement | Strength | Minimum Confidence | Expected Interpretation |
|---|---|---|---|:---:|:---:|---|
| **`SUSPICIOUS_OUTBOUND_ACTIVITY`** + **`COST_ANOMALY`** | `cost_category == "Network/Egress"` AND `bytes_sent > 10 GB` | $D(T_{\text{flow}}) \in [D_{\text{eval}} - 1, D_{\text{eval}}]$ | Exact `resource.id` | **`VERY_STRONG`** | **`0.90`** | High-volume outbound data transfer concurred with an unexpected surge in Azure network egress billing. |
| **`SUSPICIOUS_OUTBOUND_ACTIVITY`** + **`COST_ANOMALY`** | `cost_category == "Compute"` AND `anomaly_type == "MINING_PORT"` | $D(T_{\text{flow}}) \in [D_{\text{eval}} - 1, D_{\text{eval}}]$ | Exact `resource.id` | **`STRONG`** | **`0.85`** | Outbound cryptomining traffic concurred with an unexpected compute core cost surge. |
| **`RESOURCE_CREATION`** + **`COST_ANOMALY`** | `cost_category in ("Compute", "Database", "Container")` | $T_{\text{creation}} \in [D_{\text{eval}} - 7\text{d}, D_{\text{eval}}]$ | Exact `resource.id` | **`STRONG`** | **`0.80`** | Newly provisioned resource generated immediate, uncharacteristic financial run-rate vs subscription baseline. |
| **`UNEXPECTED_PUBLIC_EXPOSURE`** + **`COST_ANOMALY`** | `cost_category in ("Network/Egress", "Compute")` | $T_{\text{exposure}} \in [D_{\text{eval}} - 7\text{d}, D_{\text{eval}}]$ | Exact `resource.id` | **`MODERATE`** | **`0.70`** | Workload exposed to the Internet experienced concurrent cost increases (potential scanning/traffic influx). |
| **`SUSPICIOUS_OUTBOUND_ACTIVITY`** + **`COST_ANOMALY`** | `cost_category` NOT in (`"Network/Egress"`, `"Compute"`) | $D(T_{\text{flow}}) \in [D_{\text{eval}} - 1, D_{\text{eval}}]$ | Exact `resource.id` | **`WEAK`** | **`0.50`** | Outbound traffic anomaly coincides with unrelated cost category (e.g. Storage/Disks). Categorical mismatch. |
| **Any Security Finding** + **`COST_ANOMALY`** | Any Category | Any Window | Different `resource.id`, Same `resource_group` | **`WEAK`** | **`0.40`** | Structural co-location in resource group. No workload-level correlation asserted. |
| **Any Security Finding** + **`COST_ANOMALY`** | Any Category | Any Window | Different `resource_group`, Same `subscription` | **`NONE`** | **`0.00`** | General subscription co-existence. Suppressed as un-correlated. |

## 5. Correlation Strength Levels

Correlation strength represents the qualitative certainty of the relationship between two findings:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         CORRELATION STRENGTH TIERS                          │
├──────────────┬──────────────────────────────────────────────────────────────┤
│ Tier         │ Definition & Evidence Criteria                               │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ VERY_STRONG  │ Exact resource match + direct categorical alignment          │
│              │ (e.g. egress bytes + Network/Egress cost) + temporal         │
│              │ alignment within 24h + both findings confidence >= 0.85.     │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ STRONG       │ Exact resource match + compatible category (e.g. RC +        │
│              │ Compute surge) + temporal alignment within window.           │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ MODERATE     │ Exact resource match + broader categorical relationship, or  │
│              │ low-sample/volatile baseline.                                │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ WEAK         │ Resource group co-location only, OR categorical mismatch on  │
│              │ same resource (e.g. DNS anomaly + Disk Storage cost).        │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ NONE         │ Subscription-only match, temporal divergence > 7 days, or    │
│              │ sub-dollar cost fluctuations.                                │
└──────────────┴──────────────────────────────────────────────────────────────┘
```

> [!NOTE]
> Findings exhibiting `WEAK` or `NONE` strength **must never trigger multi-detector severity escalation** to CRITICAL.

## 6. Correlation Confidence Formulation

Correlation confidence is calculated using a deterministic additive schedule that evaluates the quality of the correlation link:

$$\text{Confidence}_{\text{corr}} = \min\left(1.0,\ \max\left(0.1,\ \text{BaseScore} + \sum \text{Adjustments}\right)\right)$$

Where `BaseScore` is the geometric mean of the two individual finding confidences:
$$\text{BaseScore} = \sqrt{\text{confidence}_{\text{security}} \times \text{confidence}_{\text{finops}}}$$

### Deterministic Adjustment Schedule

| Dimension | Condition | Adjustment |
|---|---|:---:|
| **Resource Boundary** | Exact canonical `resource_id` match | **$+0.15$** |
| | Different `resource_id`, same `resource_group` | **$-0.35$** |
| **Categorical Alignment** | Perfect alignment (e.g. Network flow bytes ↔ `Network/Egress` cost) | **$+0.15$** |
| | Compatible alignment (e.g. VM creation ↔ `Compute` cost) | **$+0.10$** |
| | Categorical mismatch (e.g. Network beacon ↔ `Storage` cost) | **$-0.25$** |
| **Temporal Proximity** | Same calendar day ($D(T_{\text{sec}}) == D_{\text{eval}}$) | **$+0.10$** |
| | Preceding calendar day ($D(T_{\text{sec}}) == D_{\text{eval}} - 1$) | **$+0.05$** |
| | Temporal distance $2\text{ to }7\text{ days}$ | **$-0.10$** |
| **Baseline Stability** | FinOps baseline mature ($N \ge 14$ days, not volatile) | **$+0.05$** |
| | FinOps baseline volatile or cold start | **$-0.15$** |

## 7. Temporal Correlation & Billing Latency Architecture

To prevent temporal misalignment due to Azure's billing batch schedule, the correlation engine strictly differentiates between three timestamps:

```
    T_event                      T_ingest (Security)                 T_ingest (FinOps)
  (14:15 UTC, Oct 07)            (14:16 UTC, Oct 07)                (06:15 UTC, Oct 08)
Workload transmits 1.5 TB        CloudPulse ingests flow            CloudPulse ingests daily
outbound network flow            telemetry and emits F-SOA-         Cost Management batch
         │                                │                                  │
         └────────────────┬───────────────┘                                  │
                          │                                                  │
                          ▼                                                  │
                 Event Calendar Date:                                        │
                 D(T_event) = "2026-10-07"                                   │
                          │                                                  │
                          │          Matches Exactly                         │
                          └──────────────────────────────────────────────────┘
                                                    │
                                                    ▼
                                       Evaluation Date from Finding:
                                       evaluation_date = "2026-10-07"
```

### Temporal Rules
1. **Never Correlate by `finding.timestamp`**:
   * Security finding timestamp reflects the near-real-time detection moment ($T$).
   * FinOps finding timestamp reflects the batch execution moment ($T+1$).
   * Comparing these directly would cause every FinOps finding to fail temporal correlation!
2. **Correlate by Event Calendar Date vs. Evaluation Date**:
   * Extract UTC calendar date from the security finding: $D(T_{\text{sec}}) = \text{timestamp}[:10]$.
   * Compare against `cost_finding.evidence.evaluation_date`.
   * Temporal correlation holds if $D(T_{\text{sec}}) \in [D_{\text{eval}} - \text{Tolerance},\ D_{\text{eval}}]$.

## 8. Multi-Stage Attack Sequences

The correlation engine recognizes three canonical multi-stage sequence archetypes:

### Sequence A: Provisioning → Exfiltration → Financial Impact
$$\text{RESOURCE\_CREATION} \longrightarrow \text{SUSPICIOUS\_OUTBOUND\_ACTIVITY} \longrightarrow \text{COST\_ANOMALY}$$
* **Archetype**: Compromised credentials or rogue automation provisions a new compute instance, uses it for data exfiltration or cryptomining, resulting in subsequent egress or compute billing spikes.
* **Interpretation**: Correlated multi-stage sequence. High priority for incident triage.

### Sequence B: Exposure → Breach Activity → Financial Impact
$$\text{UNEXPECTED\_PUBLIC\_EXPOSURE} \longrightarrow \text{SUSPICIOUS\_OUTBOUND\_ACTIVITY} \longrightarrow \text{COST\_ANOMALY}$$
* **Archetype**: An internal workload is unintentionally exposed to the Internet (e.g. port 22 or 0.0.0.0/0 NSG rule), subsequently initiates outbound C2 or mining connections, followed by billing spikes.
* **Interpretation**: Critical threat surface compromise with verified financial consequence.

### Sequence C: Direct Unbudgeted Provisioning
$$\text{RESOURCE\_CREATION} \longrightarrow \text{COST\_ANOMALY}$$
* **Archetype**: A workload is created without prior capacity planning or with an oversized SKU, producing immediate baseline deviation without observable network compromise.
* **Interpretation**: Non-malicious operational FinOps anomaly. Triage focuses on rightsizing rather than security containment.

## 10. Deterministic Severity Escalation Rules

Escalating an incident's severity requires verifiable concurrence across multiple dimensions. The engine strictly avoids simplistic formulas (such as `HIGH + HIGH = CRITICAL`).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       SEVERITY ESCALATION SCHEDULE                          │
├──────────────────────────┬─────────────────────────────┬────────────────────┤
│ Individual Findings      │ Correlation Conditions      │ Resulting Severity │
├──────────────────────────┼─────────────────────────────┼────────────────────┤
│ SOA (HIGH/CRITICAL)      │ Strength == VERY_STRONG     │                    │
│   +                      │ Category == Network/Egress  │     CRITICAL       │
│ COST_ANOMALY (HIGH/CRIT) │ Exact resource match        │                    │
├──────────────────────────┼─────────────────────────────┼────────────────────┤
│ UPE (HIGH)               │ Both UPE & SOA on workload  │                    │
```

## 11. Finding vs. Incident Responsibility

A strict invariant of the CloudPulse architecture is that **findings are immutable evidentiary records**.

```
    [Finding F-SOA-1] (Immutable) ──┐
                                     ├──► [Correlation Evaluation] ──► [Incident INC-RC-1]
    [Finding F-COST-1] (Immutable) ──┘                                   - Appends timeline event
                                                                         - Updates cost_impact
                                                                         - Escalates severity
```

* **No Finding Mutation**: Correlation never alters finding IDs, finding severities, or finding confidence scores stored in the database.
* **Incident Representation**: Correlation updates the aggregate `Incident` record by linking finding IDs into `incident.findings`, appending a correlation event to `incident.timeline`, updating `incident.cost_impact`, and elevating `incident.severity`.

## 12. Idempotency & Deduplication

### Deterministic Incident Resolution
Because all findings for a given resource resolve to the canonical incident ID:
$$\text{incident\_id} = \text{"INC-RC-"} + \text{SHA256}(\text{resource\_id.strip().lower()})[:10].\text{upper()}$$
Repeated executions of the correlation engine naturally map to the **same underlying incident**, guaranteeing idempotent storage.

### Timeline Event Deduplication
To prevent repeated batch runs from appending duplicate timeline entries:
* Before appending a `SECURITY_FINOPS_CORRELATED` timeline event, the engine inspects existing entries in `incident.timeline`.
* If a timeline entry referencing the identical pair `(security_finding_id, cost_finding_id)` already exists:
  * The engine **updates** the entry in-place if reconciled billing numbers changed.
  * It **does not append** a redundant timeline row.

## 13. Late-Arriving Cost Data Handling

Due to Azure billing latency, cost findings routinely arrive 24–48 hours after security findings. The engine handles this as a normal operational sequence:

```
  Timeline of Execution
  =====================
  Day T (10:00 UTC):
    • Attacker initiates high-volume egress.
    • SuspiciousOutboundActivityDetector runs.
    • Emits F-SOA-8C21EA4F.
    • Incident INC-RC-7A1B2C is created (Severity: HIGH, cost_impact: null).

  Day T+1 (06:00 UTC):
    • Azure Cost Management finalizes Day T billing records.
    • CostAnomalyDetector runs on daily batch.
    • Emits F-COST-4E2A91BC for Day T (evaluation_date = "2026-10-07").
    • Correlation engine runs:
        - Resolves target incident INC-RC-7A1B2C via resource_id.
        - Evaluates temporal alignment: Day T flow == Day T evaluation_date.
        - Identifies VERY_STRONG correlation.
        - Updates INC-RC-7A1B2C:
            * Populates cost_impact with verified $131.04 surge.
            * Escalates severity to CRITICAL.
            * Appends timeline event "SECURITY_FINOPS_CORRELATED".
```

## 14. False Positive & Noise Controls

The engine enforces explicit negative constraints to prevent alert fatigue:

1. **Subscription-Only Co-occurrence**: Co-locating in the same subscription never produces a correlated incident.
2. **Resource-Group Isolation**: Findings sharing a resource group but differing in resource ID are flagged as `WEAK` and never escalate incident severity.
3. **Temporal Divergence**: Security findings separated from the cost evaluation date by more than 7 days are ignored for correlation.
4. **Categorical Dissociation**: Outbound network flow anomalies are never correlated with storage or database license cost spikes.
5. **Cold-Start Suppression**: Cost findings marked with `is_cold_start = true` require an absolute delta of at least $\$100.00$ before they can be considered for security correlation.

## 17. AI & Contextual Triage Boundary

* **Deterministic Boundary**: Correlation is **100% deterministic code**. No LLM, embeddings, or probabilistic models decide whether findings correlate.
* **Role of Azure AI (Future Milestone)**:
  * Azure AI will consume the fully correlated `Incident` object.
  * AI synthesizes the human-readable summary, generates root-cause analysis, and suggests targeted remediation steps.
  * **Rule**: Correlation must execute and complete *before* the incident is presented to the AI layer.

---

## 18. Remediation Boundary

* The correlation engine **never initiates remediation actions**.
* Prohibited actions in correlation:
  * Deallocating or restarting VMs.
  * Modifying NSGs or firewall rules.
  * Revoking IAM permissions or Managed Identity tokens.
  * Altering Azure budgets or billing configurations.
* Remediation is strictly segregated into a dedicated execution engine requiring human approval.

## 20. Explicit Non-Goals

To maintain sharp boundaries, the following are strictly **excluded** from this contract:

* ❌ **No New Detectors**: No new security or FinOps detectors are defined.
* ❌ **No Modification to Existing Detectors**: `RC`, `UPE`, `SOA`, and `COST_ANOMALY` remain unchanged.
* ❌ **No Finding Schema Redesign**: Existing `Finding` and `EvidenceInfo` models are preserved.
* ❌ **No Incident Schema Redesign**: Operates strictly within existing `Incident` model.
* ❌ **No Machine Learning or Forecasting**: Zero probabilistic heuristics or clustering algorithms.
* ❌ **No Hardcoded Azure Pricing Tables**: Zero rates per GB or static cost models.
* ❌ **No Automated Remediation Execution**: Zero infrastructure modifications.
* ❌ **No Generative AI / LLM Implementation**: Natural language generation belongs to the AI triage layer.
* ❌ **No Database Migrations**: Uses existing PostgreSQL `incidents` schema and JSONB fields.
* ❌ **No Terraform Changes**: Zero cloud resource changes.
